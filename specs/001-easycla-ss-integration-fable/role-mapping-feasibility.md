**For**: Heather (PM), Kieran (strategy) | **From**: Michal (engineering) | **Date**: 2026-07-15
**Basis**: [00-overview-fable.md](00-overview-fable.md) §2.4/§3, [04-milestone-ccla-org-lens-fable.md](04-milestone-ccla-org-lens-fable.md) role options, code verification 2026-07-15
**Answers**: the open engineering action from the 2026-07-15 leadership review ([spec.md](spec.md) "Program review outcomes")

## Executive answer

**Feasible with conditions — and the conditions are smaller than we assumed.** Self Serve can call the existing EasyCLA v4 APIs with user-scoped tokens without any gateway or EasyCLA changes, because the entire v4 authorization chain keys on the **user's identity (LF username), not on which Auth0 client or audience minted the token**: the gateway validates issuer only (audience check is explicitly disabled), resolves the user's ACS permissions per request, and injects them as an `X-ACL` header that v4 trusts wholesale. Self Serve already ships the exact token machinery needed (a secondary access token for the `api-gw.*.platform.linuxfoundation.org` audience, minted from the user's refresh token) and that audience is precisely the one Auth0 stamps the required `lfx.dev/claims/username` claim onto. The Corporate Console today sends an Auth0 **ID token** and it works — direct evidence that audience is irrelevant. The recommendation from milestone 04 stands: **Option A (bridge) for M4/M5, OpenFGA modeling deferred to M6, org-admin mapping rejected.** The two conditions to convert to facts before committing M3–M5 staffing: (1) confirm ACS's gateway-level path authorization admits ordinary users (no CLA role) to the v4 *read* endpoints M1/M3 need, and (2) confirm the refresh-token exchange for the api-gw audience is granted to the SS Auth0 client in each environment. Both are one-day curl spikes (§5).

## 1. Where v4 actually enforces CLA roles (verified in code)

Enforcement happens at **two layers**, and neither is "v4 checks roles":

**Layer 1 — lfx-gateway (per request).** All non-public `/cla-service` paths run the `secured` chain (`lfx-gateway/dynamic/services/cla-service.yaml:45-53`): a JWKS middleware validates the JWT **signature and issuer only** — audience validation is commented out ("Skip requiring audience for now", `lfx-gateway/dynamic/middleware.yaml:35-36`) — then the ACS authorizer plugin calls ACS warden (`/v1/api/warden/subjects/authorize/v2`) with the username, URL path, and HTTP method, **403s if ACS says not allowed** (`traefik-acs-authorizer-middleware/acs.go:399-401`), and otherwise injects the user's resolved scopes as a base64 `X-ACL` header plus `X-Username`/`X-Email` (`acs.go:410-419`). A significant set of v4 paths bypass this entirely on a public router — health, `request-individual-signature`, `user-from-token`, `notify-cla-managers`, the designee-check, the cla-group manager list, and more (`cla-service.yaml:4-38`).

**Layer 2 — v4 handlers (scope tuples, not roles).** v4 does **no JWT validation of its own** for `/v4`: `v2API.LfAuthAuth = lfxAuth.SwaggerAuth` (`cla-backend-go/cmd/server.go:481`) simply base64-decodes the `X-ACL` header into an `authUser` (`lfx-kit@v0.1.33/auth/handlers.go:76-82`). Handlers then compare scope **type + ID** against the request's project/company SFIDs; the scope's `Role` field is never consulted in these checks (`cla-backend-go/utils/utils_user_auth_lambda.go`, all helpers; `lfx-kit/auth/user.go:91-127`). Role-specificity therefore lives in **ACS's policy mapping** (which roles produce which scopes for which resource×action), not in EasyCLA code.

| Endpoint group | What's checked | Where | Notes |
|---|---|---|---|
| Approval list `PUT /signatures/project/{p}/company/{c}/claGroupID/{g}/approval-list` | project\|org tree scope from X-ACL; **staff-admin scope disallowed** | `v2/signatures/handlers.go:96,121` | Plus gateway warden check |
| CLA manager `POST/DELETE …/cla-manager` | project\|org tree scope; admin disallowed | `v2/cla_manager/handlers.go:64,116` | Write also dual-updates signature ACL + ACS role (`v2/cla_manager/service.go:242,405`) |
| CLA manager **designee** `POST` | **Nothing** — "anyone can assign a CLA manager designee...no permissions checks" (code comment) | `v2/cla_manager/handlers.go:159-161` | Also on the gateway's public router for the invite variants |
| `POST /request-corporate-signature` | project\|org tree scope; admin disallowed | `v2/sign/handlers.go:123` | |
| `PUT …/ecla-auto-create` | **Signature-ACL membership** (`CurrentUserInACL`), *not* ACS scopes; + persisted sanctions flag | `v2/signatures/handlers.go:1335-1350` | A second, DynamoDB-resident source of manager truth |
| CLA group admin ops (project lens) | project / project-tree scope; **staff-admin allowed** | `v2/cla_groups/handlers.go:476,561,588` | |

Two consequences worth naming plainly. First, **enforcement is uneven**: designee creation is unauthenticated-by-design, ecla-auto-create checks a different store (signature ACL) than approval-list edits (ACS scopes), and staff admins can administer CLA groups but *cannot* touch approval lists or managers. SS should mirror v4's decisions rather than re-derive them, or it will disagree with the backend at exactly these seams. Second, **v4 trusts `X-ACL` unconditionally**; I found no authorizer or API-key requirement on the v4 stack itself (`cla-backend-go/serverless.yml` — no `authorizer`/`apiKeys`; the Corporate Console BFF's `X-API-KEY` header appears to be required by nothing in this repo). Whether the Lambda's non-gateway URL is reachable with a forged X-ACL is **unverified** — spike 4 below; out of scope for this memo but a hardening item to file.

## 2. Token path: what v4 expects, and whether SS has it

What "v4 accepts a token" really means, given §1: **the gateway accepts it and ACS knows the user**. Verified chain:

- The Corporate Console's permission strings (`signature_approval_list:update:project|organization:…`) are **not token claims** — the console BFF fetches them at runtime from user-service `GET /user-service/v1/me/permissions` and checks them via `POST …/me/permissions/checks` (`lfx-corp-cla-console/backend/src/data/user-api.ts:27-44,160-164`). The BFF then calls v4 with the user's raw Auth0 **ID token** (`backend/src/data/cla-api.ts:30`). An ID token has no API audience at all — proof the gateway's audience check being disabled is what the current system relies on.
- The gateway needs the token to carry `http://lfx.dev/claims/username` (its JWKS middleware exports it to the ACS plugin via header, `middleware.yaml:37-42`; missing username → 403 at `acs.go:328-331`). Auth0 stamps that claim on **access tokens whose audience matches `https://api-gw.(env.)platform.linuxfoundation.org/`** (`auth0-terraform/src/actions/custom_claims.js:387-395`).
- **Self Serve already mints exactly this token.** `extractApiGatewayToken()` exchanges the session's refresh token for a second access token with audience `API_GW_AUDIENCE` (`lfx-self-serve/apps/lfx-one/src/server/middleware/auth.middleware.ts:230-249`; `.env.example:146` sets it to `https://api-gw.dev.platform.linuxfoundation.org/`), cached in the session. This is a **user-scoped** token (the crowdfunding precedent's mechanism, `server/utils/refresh-token-exchange.util.ts:20-101`).

**Finding: no token exchange *project* is needed — it's already built.** The M1 research (R3) framed "will v4 accept SS's audience" as the spike; the code answer is that audience never mattered — identity does. The residual unknowns are operational, not architectural: (a) is the SS Auth0 client authorized for the api-gw audience grant in dev/staging/prod (the exchange currently uses `PCC_AUTH0_*` credentials — `auth.middleware.ts:237-241`); (b) does ACS warden **allow** an ordinary SS user (no CLA/ACS roles) through the gateway for the secured v4 *read* paths M1 needs (e.g. `GET /signatures/user/{id}`)? If warden denies role-less users on those paths, the fix is an ACS policy entry or an M2M fallback with SS binding the subject server-side — contained either way. Inference, to be spot-checked: since contributors (role-less users) use the Corporate/Contributor consoles today mostly via the *public* router paths, warden behavior on secured read paths for role-less users is genuinely unknown.

## 3. Read path for SS UI gating

How SS learns "user X has CLA authority over company Y / CLA group Z", assessed:

| Candidate | Auth needed | Latency | Staleness | Verdict |
|---|---|---|---|---|
| `GET /v4/company/{id}/cla-group/{g}/cla-managers` | **None** (public router, `security: []`) | 1 DynamoDB read | Reads the CCLA signature ACL — the same store `ecla-auto-create` enforces; updated synchronously by manager add/remove | **Use** for "is user a manager of this company×CLA group" |
| `GET /v4/company/{id}/project/{sfid}/cla-managers` | Org scope on the company (admin allowed) (`v2/company/handlers.go:144`) | gateway+ACS+DDB | same | Use where org context already established |
| user-service `POST /me/permissions/checks` (console's method) | User's api-gw token | ACS resolution; ACS caches role-scope reads ~30 min (`acs/middleware/cache.go`) | **Up to ~30 min stale** — overlaps badly with the async designee flow | Use only for coarse gating; never for post-assignment confirmation |
| ACS rolescopes APIs (`GET /organizations/{id}/roles/{roleId}` etc., `acs/userrole/transport_http.go:38-43,106-111`) | Service-level (M2M) | Postgres direct | 30-min middleware cache on some routes | Fallback for admin/reporting views; not per-request UI gating |
| `cla-{stage}-user-permissions` DynamoDB table | — | — | — | **Reject**: feeds only the v3 OAuth authorizer's project scope (`cla-backend-go/user/repository_dynamo.go:114`, `auth/authorizer.go:148`); not v4 truth |
| Optimistic call-through: attempt the v4 read/write, treat 403 as "no authority" | User's api-gw token | one round trip | **Zero** — it *is* the enforcement answer | **Primary pattern** for actions |

**Recommendation**: gate SS UI on the two signals that enforcement itself uses — the signature-ACL-backed cla-managers endpoint for "manager of company×group" views, and optimistic v4 calls (403 ⇒ hide/disable) for everything scope-based. Avoid building a permission-string evaluator in SS: the strings are an ACS/console vocabulary, they're 30-minutes-stale, and v4 doesn't check them — it checks scopes resolved at request time.

## 4. Options assessment (confirming/overturning milestone 04)

**A. Bridge — confirmed, and cheaper than milestone 04 assumed.** The milestone-04 concern "v4 might not accept SS tokens without gateway changes" is resolved negatively: no gateway change, no EasyCLA auth change, no new token infrastructure (§2). Residual costs: the two spikes' outcomes (possible small ACS policy addition), and inheriting today's failure modes unchanged — async ACS assignment (server-side retries stay in SS, as in the console's 30× polling), the documented one-company-at-a-time role limitation (a data/UX constraint the bridge can *surface* but not fix — org-lens UX must handle "you have CLA authority here, but your role is attached to another company"), and the enforcement unevenness in §1 which SS must mirror, not mask.

**B. OpenFGA copy now — still rejected for M3–M5, evidence strengthened.** The copy would be non-enforcing (v4 checks X-ACL/ACS and signature ACLs; no FGA CLA types exist — `lfx-v2-fga-sync/docs/fga-catalog.md`), and §1 shows there are *two* upstream truths to sync (ACS scopes *and* signature ACLs), doubling the divergence surface. ACS's own 30-min read cache already causes UI-vs-enforcement drift today; adding a third eventually-consistent copy on top of an async assignment pipeline is the "SS says I can, EasyCLA says I can't" scenario. Correct time to model CLA in FGA is M6, when enforcement moves.

**C. Org-admin = CLA manager — rejected, now with a hard blocker.** Beyond the legal/product semantics change: v4's write paths check **project|organization tuple scopes** with staff-admin explicitly disallowed (`DISALLOW_ADMIN_SCOPE`, §1). `b2b_org#writer` has no project dimension, so mapping it onto CLA authority either grants approval-list control per-company-across-all-projects (a semantics change) or requires rewriting v4 enforcement (that's M6, not a UI milestone).

**Net: recommendation A stands.** The role difference is a contained adapter in the SS `cla` server module, per the program strategy.

## 5. Spike list (dev environment, curl-level; each ≤ half a day)

1. **SS token → secured v4 read.** Exchange a dev SS session's refresh token for the api-gw audience (`refresh-token-exchange.util.ts` flow), then `GET /cla-service/v4/company/{id}/project/{sfid}/cla-managers` as a known CLA manager. **Expected**: 200 with manager list; decodes the whole chain (claims → gateway → warden → X-ACL → v4 scope check). A gateway 403 here means an ACS policy/grant gap — capture the warden request/response.
2. **Role-less user → M1 read path.** Same exchange for a user with no ACS roles; `GET /cla-service/v4/signatures/user/{their-userID}`. **Expected outcome unknown — this is the decision point**: 200 ⇒ M1 uses user tokens as designed; 403 ⇒ file the ACS policy addition or fall back to M2M + server-side subject binding.
3. **Write path end-to-end.** As a dev CLA manager with an SS-minted token, `PUT …/approval-list` adding a test email. **Expected**: 200 and the approval list updates — proves M4 writes need no further auth work. Then repeat as a non-manager: **expected** 403 *at the gateway* (not v4), confirming where denial surfaces for UX copy.
4. **X-ACL forgery check (hardening).** Call the v4 Lambda's non-gateway URL (us-east-2 execute-api / `api.lfcla.*` domain) with a hand-crafted `X-ACL`. **Expected**: blocked by some layer we haven't identified; if it succeeds, file a security issue immediately (independent of this program).
5. **Designee propagation clock.** `POST …/cla-manager-designee` for a test user, then poll user-service `me/permissions/checks` and the cla-managers endpoint, timestamping when each turns positive. **Expected**: cla-managers (signature ACL) flips fast for full managers; permission strings lag (ACS async + 30-min cache) — this number calibrates SS's retry budget and "pending" UX for M3/M4.
